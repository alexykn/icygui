# Scale benchmark

`generate.py` writes an Icinga 2 config with N hosts × 15 services (about 5% problems, realistic outputs, perfdata and vars). `benchmark.sh` starts a real Icinga 2.15 in Docker with it and measures load sizes and times and a forced re-check burst on the event stream. The results and the design they led to are in `docs/performance.md`.

`starts.sh [hosts] [clients]` (default 2000 and 20) starts the same Icinga in a container of its own and measures many icygui engines starting at once, first as users opening the app, then (on the restarted Icinga) as background starts with their size-proportional wait (PERF-09): when they were connected, the master's peak memory (`docker stats`) and the response time of a small by-name query that another client sends every half second (at rest and during the starts). `PHASES` chooses the phases, each on a freshly restarted Icinga: `user`, `background` (the default factors) and `background:<ms per 1 000 services>:<max s>` to compare other factors, e.g. `PHASES="user background background:1500:45" contract/scale/starts.sh 2000`. Two more calibrate the request budget and the reconcile factor: `budget:<ms per request>` (0: no budget) has every client fetch an outage's problem details by name at once (`ICYGUI_SCALE_BATCHES` requests of 200 services in full, 140 by default: 28 000 problems), and prints how long it took, the master's CPU time (its cgroup's accounting, minus what it spends at rest), memory and response time to another client; `reconcile` has one client run the lean reconcile's queries and prints the master's CPU time per reconcile and per 1 000 objects, e.g. `PHASES="budget:200 budget:500 budget:100 budget:0 reconcile" contract/scale/starts.sh 2000`. It runs `ic-core`'s ignored `starts` tests, which refuse anything but that local container, and removes the container and its volume at the end. Results in `docs/performance.md` (*Quiet mode and load pacing*).

`fleet.sh <scenario>` measures many icygui clients on one master for a long while, against the demo cluster at the user's size (`ICYGUI_DEMO_SCALE_HOSTS=2000 demo/up.sh`; never anything else: it checks the URL is this machine, the fixture-only `viewer` logs in, the node is the compose project's `master-01`). It runs `ic-core`'s ignored `fleet` test (real engines in one process, started, switched between live and quiet, and stopped by commands through a FIFO) on some cores and the cluster's containers on the others (`docker update --cpuset-cpus`), and measures from outside: the master's cgroup CPU time and memory every second (`fleet_sample.py`, also the client process and Icinga's JSON-RPC queues and HTTP clients every 5 s), its answer time to another client's small by-name query and to an Icinga Web style command (a passive result by filter for a marker service, whose state flips every second, so the engines' `delays.csv` gives the delay from a check result to each client) every second on a fresh connection (`fleet_probe.py`, at real-time priority; open-loop since the settling of 2026-10-11: each second's request goes out on schedule on its own thread, a stall shows in every second it lasts, and `fleet_analyse.py` re-scores the earlier closed-loop runs the same way), and problem storms through master-02 (`fleet_storm.py`). Scenarios (the list with their durations is at the top of `fleet.sh`): `steady` (0, 1, 10, 25, 50 clients, 30 minutes at 50, a storm), `events` (50 clients, a storm, all 50 live), `restart` (a restart and a reload of master-01 with `FLEET_CLIENTS` clients), `morning` (50 windows opening within 3 minutes, 50 starts at login at once), `fit` (bare event streams at rest and under a storm: the master's CPU per stream; the streams are read by `fleet_streams.py`, which times when the marker's results arrive, the master's own delivery delay with no client behind it, and each step waits until master-01 is back at rest), `reconcile` and `quiet_reconcile` (periodic reconciles every 5 minutes: what they find and cost), `smoke`. Each run's directory in `fleet-data/` is named after its scenario; `restart-50` and `restart-40` are the `restart` scenario with 50 and 40 clients, `fit-5000` the `fit` scenario with `FLEET_STORM=5000 FLEET_STORM_S=30`, `fit-dedicated` the same on a dedicated master-01 (`FLEET_M1_CPUS=0,1 FLEET_OTHERS_CPUS=2 FLEET_CLIENT_CPUS=3 FLEET_RAW_DIRECT=1`, the settling's re-run), `icinga-master-01.log` master-01's warnings and work-queue lines over all runs. `fleet_analyse.py <run dir>...` prints the tables. The raw data of the 2026-10-11 runs is in `fleet-data/` (gzipped); the results are in `docs/performance.md` (*Fifty clients on one master*).
