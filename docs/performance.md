# Performance at production scale

**Requirement:** the production Icinga has about 2 000 hosts. Icinga Web shows them accurately, stays smooth, and reflects changes in time. icygui must do at least as well, over the Icinga 2 REST API only (no direct Redis/SQL access, see below).

## How Icinga Web does it

From the Icinga DB documentation:
- Icinga 2's *Icinga DB feature* publishes configuration, state changes and check results into **Redis**.
- The **Icinga DB daemon** copies them into a relational database (MySQL/PostgreSQL).
- **Icinga DB Web** reads current host and service state from Redis and everything else from SQL.
- It only ever renders **one page of rows** (filtered, sorted and paginated by the database with indexes) and refreshes that page every few seconds.
- Actions go through the Icinga 2 REST API ("command transport").

So the browser never holds all objects, and "in time" means "at the next auto-refresh".

**Why icygui doesn't do the same:**
- A desktop client reading Redis and SQL directly would need Icinga DB's Redis (normally unauthenticated and bound to the master) and the database reachable from every engineer's laptop.
- It would bypass Icinga's per-user API permissions.
- It would couple the client to internal schemas that change between Icinga DB releases.
- It would still need the REST API for actions.

The REST API is the stable, public, permissioned interface. The design below makes it scale.

## Measurements

**Where and when.** Every measurement in this document ran in the project's development container: 4 vCPUs (Intel Xeon @ 2.10 GHz), 15 GiB of RAM, Linux, with the Docker Icinga (`icinga/icinga2:2.15`, which reports 2.15.6) on the same machine, so the master and the clients shared those four cores. Each section names its date and the commit that recorded it; the commands to run them again are next to the numbers. Later engine changes (for example 073e8f2, a reconcile's tier 3 and the wake-up refresh, 2026-10-06) were not measured again.

Measured 2026-10-05 (commit 7e803cd) against a real **Icinga 2.15.6** in Docker with **2 005 hosts and 30 006 services**:
- 5-minute check intervals, about 5 % service problems;
- realistic outputs with perfdata, and custom vars;
- generated by `contract/scale/generate.py` and reproduced by `contract/scale/benchmark.sh`.

|---|---|

| Services, every attribute the client needs | **46.4 MB, 3.66 s** |

The lean list the client loads (`ic_api::Detail::Lean`) keeps the check configuration, the `enable_*` switches and `flapping_current`, and leaves out `last_check_result` and the links (`notes`, `notes_url`, `action_url`, `icon_image`). It wasn't measured on this instance: those attributes add about 210 bytes per service on the contract instance, and `ic-mock`'s `large` scenario, whose full and all-attribute sizes match the table, gives **26.5 MB** (884 bytes per service; about 2 s at the rate above).

**Conclusions:**
1. `last_check_result` is 64 % of a service's bytes (it includes the full command line, `vars_before`/`vars_after` and perfdata). Loading it for 30 000 OK services the user isn't looking at is wasteful.
2. Large responses make the *master* allocate around 1 GB that it keeps. One full reload per minute from each colleague's laptop would hurt the master, so **periodic full reloads are not acceptable at this scale**.
3. The event stream already carries everything needed to keep state current. `CheckResult` events include `vars_after` (`state`, `state_type`, `attempt`, `reachable`), `downtime_depth` and `acknowledgement`, so **no per-event re-queries are needed**.
4. The client must absorb about 5 000 events/s bursts (after an Icinga restart or a mass re-check) without stalling the stream; otherwise Icinga buffers the backlog in its own memory.

## Design

**Tiered loading:**
1. Hosts: full (0.4 s). The sidebar, host problems and dashboard counts become usable first.
2. Services: lean attributes, no `last_check_result` and no links (about 2 s). States, handled flags, severity and every dashboard count are exact at this point, except for filters on the check output (`last_check_result`) or the links, which see those only once the object is loaded in full (step 3, 5) or, for the output, by its next `CheckResult` event (step 4). The check configuration and the switches are in the lean list because no event ever brings them. A lean service with `last_check = -1` is pending; otherwise its output is "not loaded yet".
3. Check results and links for every service in a problem state, by name (0.14 s for 1 473). Problem lists are complete.
4. From here, every `CheckResult` event carries its object's full result, so outputs fill in by themselves within one check interval.
5. *Hydration on demand:* rows on screen whose output isn't loaded yet (an "all services" dashboard, a host pane's service list) are fetched by name in debounced batches (≤ 200 names). Opening a pane fetches that object in full (output, perfdata, notes and links).
6. Never `filter` expressions (permissions, D6), only name lists. A name list containing a deleted object fails as a whole (404), so retry by halves to find the deleted names.
7. Icinga's own `Notification` objects (whom Icinga notified, and when: the panes' "notified" row) load last, in the background, with four attributes each (about 200 bytes per object). Icinga's `Notification` events keep them current (the object's notifications are re-read by name), so periodic reconciles and `Refresh` leave them out; reloads after a long gap and restarts reload them.

**Event pipeline:**
- A *reader* task only reads and splits lines and hands them over; it never waits for processing, so Icinga's send buffer never backs up.
- An *applier* parses and applies events in batches:
  - `CheckResult` updates the object completely from `vars_after`, `downtime_depth` and `acknowledgement`. `next_check` is estimated from `execution_end` plus the check or retry interval.
  - Several `CheckResult`s for one object within a batch collapse to the last one.
  - `StateChange` and the other event types are never collapsed (rules and the event log need every transition).
- Re-queries happen only for `ObjectCreated`/`ObjectModified`/`ObjectDeleted` and for unknown objects. Unknown objects are looked up in whole batches (one request per 200 names, no bisecting) and names that come back missing wait longer each time (10 minutes, doubling up to 4 hours; an event during the lookup waits for its answer instead of asking again): an API user with filtered permissions receives every object's events but may query only some, and bisecting each hidden name would cost two requests per name (about 54 000 requests every 10 minutes for a user who sees a tenth of 30 000 objects).
- Snapshots go out at most 4 times per second. Dashboards are re-evaluated only for touched objects and re-sorted only when their rows or sort keys changed.

**Freshness watchdog** (instead of refreshing by schedule):
- Every object has a deadline: Icinga's own `next_update`.
  - Active checks: `next_check` + the check or retry interval + 2 × latency.
  - Passive checks: last result + 2 × interval.
  - It isn't loaded (`next_update` exists only from Icinga 2.12, and the model has no field for it): it's computed locally with Icinga's formula (`Checkable::GetNextUpdate`) from the lean attributes, and recomputed from every `CheckResult` event.
- Each event, whether a scheduled check, a manual "check now" by anyone, or a passive result, resets that object's deadline. Manual runs by colleagues therefore never desynchronise anything.
- An object with no result past its deadline is re-queried by name (batches ≤ 200, at most once per interval per object). That cheaply catches missed events, and it corrects deadlines after someone reschedules a check without an event.
- A stream that stalls without closing (a proxy that stops relaying; Icinga sends nothing on an idle stream) is noticed by the status poll: active checks in the last minute but no line for 2 minutes reconnects.
- If Icinga still reports the object overdue after the re-query, the check is genuinely **late**. The UI marks it ("late 12m"), as Icinga DB Web does. A satellite or agent has usually stopped checking.

**Reconciling (keeping the client and Icinga in sync):**
- Finding the node on connect (ENV-12): at each URL tried, a login (`GET /v1`), the node's name (`/v1/status/IcingaApplication`) and the zone tree (`/v1/objects/zones`, a few hundred bytes per zone); only the node taken gets the event stream. While connected to a satellite (a partial view) the preferred URLs are asked the same three small questions after 30 s, then less and less often (up to every 10 minutes, half of each wait jitter); a node that sees the whole cluster asks nothing more. A URL that doesn't answer these within 8 s is passed over while others remain (it isn't held for the 30 s request timeout), and a reconnect after a failover asks the master that took over first. Coming back from a satellite to a master costs one jittered full reload and nothing else: events about the objects the satellite didn't have wait for that reload instead of being looked up by name.
- A lean load (tiers 1–3) on connect. A failing first load is retried after 30 s, doubling up to 15 minutes, not with every quick reconnect; an answer the client can't read isn't retried.
- A lean reload after a reconnect only when the stream was silent for 2 minutes or more (a laptop that slept, an outage), with jitter so ten clients reconnecting together don't hit the master at the same instant. After a shorter gap the events since bring every object checked again and the periodic reconcile the rest: a proxy or load balancer that ends the stream every few minutes (a maximum response time) would otherwise cost a full reload (about 41 MB with the `Notification` list) each time.
- A periodic lean reconcile, **adaptive**, following the installation's size (see *Load pacing* below): every 5 minutes up to about 10 700 objects, 15 at 32 000, stretched up to an hour while the stream stays continuous; at least 30 minutes in quiet mode. It's configurable, but never below 5 minutes from 5 000 objects on (a lean reload of 30 000 services every minute is about 34 MB a minute per client). Its tier 3 fetches only the problems the client doesn't hold in full with a current result, so an outage with 28 000 problems doesn't cost 140 full-detail requests every interval. A failed reload waits one to two intervals from the failure (a random phase, never less than a whole interval). Each client's reconciles are spread so that clients never line up (*No synchronised clients* below).
- The switcher's node list (ENV-06): the zones and endpoints come with the load (the requests that already found the node, no extra one); afterwards each status poll asks for the `connected` flag of the nodes next to the connected one (its zone's, its parent zone's and its child zones' endpoints; agents never) in one small by-name request (`/v1/objects/endpoints`, `attrs: ["connected", …]`: since the cluster health page also the version, last message and message rates, in the same request, about 100 bytes per node): every 30 s for the environment on screen (every 5 minutes, with its status poll, while its window is hidden in quiet mode), every 5 minutes for the others whether quiet or not, and at once (with a status poll) when an environment comes on screen with states older than 30 s. Nothing is asked without the `objects/query/Endpoint` permission.
- The cluster health page (topic 06, ENV-13): its trends are kept in memory from the status poll above (no request of their own). Only while the page is on screen in a window that isn't hidden, and never while the environment is quiet, each status poll also asks for `/v1/status/ApiListener` (about 1 KB), and the page asks for the node's features (`/v1/objects/{checkercomponents,notificationcomponents,icingadbs}`, `attrs: ["paused"]`, a few hundred bytes each) when it opens and every 5 minutes; each of these takes a token from the request budget. Clicking on the page asks nothing. A closed page costs nothing.
- An Icinga restart (a node's `program_start` changes in `/v1/status`, polled every 30 s) triggers a reload, at most every 30 s; another node of an HA zone answering behind a load balancer doesn't, and neither does the second master of a deploy that restarted both once a reload since the reconnect brought everything. `Refresh` reloads like a reconcile (Icinga's notifications stay while the stream keeps them current) at once, then spaced 30 s, 2 min and 5 min apart while it keeps being pressed; more requests coalesce.
- An action's effect comes with Icinga's events; its targets are queried by name only when the stream lacks those event types (a forced check of 5 000 services would otherwise cost 25 by-name queries of the state from before the checks, while Icinga runs them).
- **Downtime depths.** A downtime event that changes the count of an object whose count came from a query answer makes it provisional: the answer may already have counted it, and a count applied twice would hide a problem in quiet mode (docs/architecture.md, *Downtime depth*). Every load and reconcile is such an answer, so after each one (every 5 to 60 minutes live, 30 or more quiet) every count is an answer's until the object's next check event: the cost recurs, in live mode too, and every client reads the same downtime events at the same moment. So only **problems** are asked for again by name (an OK object's count can't hide anything, and the state change that makes it one brings Icinga's count), through the re-query queue and the request budget, each **spread** by a random delay of up to 2 s per request it takes (200 names, at most 30 s), and a failed request is retried after 5 s, doubling up to 5 minutes. A schedule that starts downtimes on 30 000 services of which 900 are problems costs each client 5 requests within about 10 s, so 50 clients spread 250 small requests over those 10 s; before the small fix 3 fixer every object was asked for, 150 requests per client at the same moment (7 500 for 50 clients, each a lean reload's worth). The same again when the downtimes end. These are estimates from the code, not measured (the cluster tests only check that the answers are right, at small scale; `starts` on the scale workload would measure it).
- Never periodic full-attribute reloads.
- **Several environments** (PLAN.md D2): every saved environment runs its own engine all the time, so each Icinga cluster sees at most what it saw when it was the only environment: one event stream and the loads above, and in quiet mode (below) a stream without check results. Engines off screen do nothing more: no hydration (only the window asks for full details of rows on screen), no extra reloads, and switching environments reloads nothing. They publish their snapshots at most every 2 s instead of every 250 ms (only the tray and the switcher read them), except when a notification waits for its dashboards, which keeps their notifications as prompt as the active one's. The client's own cost grows per environment (a store, a log and the dashboards' evaluation each); the master's doesn't.

## Quiet mode and load pacing (PERF-09)

**Why.** The real ongoing cost of a client on the master is its event stream: Icinga encodes every event once per connected client, and almost all of it is `CheckResult` (one per check, about 110 a second at 2 000 hosts and 30 000 services). Fifty colleagues each running icygui cost the master 50 × 110 events a second, nearly all of them for windows nobody looks at. And the first load is the biggest single cost of a client: a team starting its laptops at nine loads at nine.

**Quiet mode** (the general setting *Quiet mode when hidden*, on by default) applies to every environment that isn't on screen and to the one on screen while the window is hidden: once it has been out of sight for 30 s, closed to the tray or not shown at all as the system reports it (GPUI's window visibility: minimised, another virtual desktop or Space, a sleeping display, on macOS also completely covered); never to a window that is merely unfocused or partly covered (a dashboard on a second screen stays live). The 30 s keep a quick look elsewhere (Alt-Tab over a full-screen window) from switching the stream, since every switch opens a new stream on the master for a moment; showing the window counts at once, before anything opens in it. There is deliberately no per-environment or per-dashboard exception: the stream can't be narrowed per object without the `filter-expression` permission (which icygui avoids, and Icinga 2.17 restricts), so one exception would put the whole environment back on the full stream, and notifications don't need one.
- The stream subscribes to every type but `CheckResult` (`ic_model::EventKind::QUIET`): state changes (soft and hard, each with the check result that caused it), acknowledgements, comments, downtimes, flapping, Icinga's notifications and configuration changes still come at once, so **notifications are never delayed**.
- The status is polled every 5 minutes instead of 30 s, the reconcile runs at least every 30 minutes, there is no freshness watchdog, no hydration, snapshots go out every 2 s (a waiting notification still goes out at once), and the dashboards keep only the memberships notification decisions need: rows and summaries, which nobody sees, are rebuilt on waking up.
- Stale while quiet: outputs of checks that didn't change the state, last-check times, late markers. A quiet stream can be silent for many minutes, so stalls are found differently: Icinga's service counts by state (from `/v1/status/CIB`) only move with a state change, which comes with an event; counts that moved while nothing arrived mean a stall (reconnect and reload).
- **Switching without a gap or a duplicate:** Icinga can't change a stream's types, so a switch opens the new stream while the old one keeps being applied. Icinga subscribes a stream before it answers the request, so once the new one is open it has everything sent from then on; both are read side by side until a line comes on both (the old one has then delivered everything sent before the new one subscribed; at most 7 s), the old one closes, and the new one's waiting lines are applied without those the old one brought (the same event is the same line on both: Icinga encodes it from the same dictionary). Tested with bursts of state changes and a downtime removal landing in the overlap, both ways (`tests/engine/quiet.rs`).
- **The window outlasts Icinga's batches (measured, Icinga 2.15.6 on the demo cluster, 2026-10-10):** Icinga writes each event stream in batches 5.0 s apart, idle or busy (a raw stream showed bursts at 0, 5.0, 10.0, 15.0 s whose oldest event was 5.0 s old and newest fresh); a new stream's first events go out at once. The old 2 s window therefore closed the old stream before its next batch on nearly every switch, and what it still held from before the switch was lost: during the cluster test's problem storm (40 services, 14 switches) all 14 handovers went without proof and the soft attempts of about 38 services never arrived, until the status counts made a reload find them hard about 15 s later. With 7 s the old stream's batch comes inside the window and brings the line both streams carry: the same test logs every storm problem soft before hard and notifies each once (`cluster_switching_modes_during_a_problem_storm_logs_and_notifies_each_change_once`, three runs); `a_switch_keeps_the_old_stream_until_its_next_batch` holds the old stream's lines in `ic-mock` for 3 s to keep it so. The window bounds the wait, and it costs something: the old stream's lines are applied as they come, but the new stream's wait in a buffer until a line comes on both streams or the window ends, so on a calm installation (no line on both, below) a switch to live applies the live stream's check results up to 7 s late (2 s before). What is on screen doesn't wait for them: the object being opened and the rows on screen are asked for by name at once, and so is the refresh of the other problems after waking, as soon as the live stream is subscribed (its answers are ordered against that stream's lines like any query's; `the_refresh_after_waking_does_not_wait_for_the_handover`).
- **A switch without that proof** (no line on both streams within the 7 s: the usual case on a calm installation, where neither stream says anything for seconds) may follow an old stream that had stalled or lagged. Such a switch costs one status poll (two small requests): Icinga's service counts by state, compared with the store's against the offsets of the polls answered while the old stream still delivered lines, must not have moved apart (a mismatch confirmed by the next poll means it withheld state changes, and a jittered reload brings them). Tested by stalling the old stream before a switch in both directions: the withheld problem notifies about 0.7 s after the switch, and a switch that missed nothing costs no reload.

**Waking up instantly** (opening an object that went red must feel faster than 1–2 s):
1. A state change carries its full check result (output and performance data, `contract/samples/events.ndjson`), so an object that went red is in the store already.
2. A notification icygui shows fetches its object in full right away (one small request; silent ones, such as those a storm summary covers, fetch nothing; at most 10 a minute), so a click finds a complete pane.
3. The object being opened (`Command::Focus`) gets one by-name request of its own before anything else, ahead of the request budget, unless the store holds it current; then the rows on screen whose output may have changed (the app offers every row on screen; the engine takes them out of the refresh below, so they come right after the opened object however low they rank); then the problems whose output may have changed meanwhile (at most 1 000, most severe first), asked for as soon as the full stream is subscribed, without waiting for the switch's handover.
4. The pane never blocks: it renders from the store and fills in; while `Snapshot::updating` lists its object for longer than 300 ms, its header shows `updating…` in a slot of fixed width (nothing moves when it comes and goes).
5. The app asks for the object a pane shows the moment it opens (a click, Enter, a notification's click, the palette), and when the list's cursor moves with the keys once it rests for 150 ms, so holding `j` costs one request for the row it stops on; after waking up it asks again, and the rows on screen are asked for again (the engine dropped what was asked for while quiet).

**Load pacing that scales with the installation:**
- *Background starts* (launch at login): `delay = random(0, min(90 s, 3 s × services / 1 000))`, the size read from `/v1/status/CIB` first (two small requests; without `status/query`, 15 services per host from a list of the hosts' names, about 240 KB at 2 000 hosts). 200 services wait under 0.6 s, 3 000 up to 9 s, 30 000 up to 90 s. A start the user opens never waits, and opening the window ends a wait. The event stream is open during the wait: a problem that begins meanwhile notifies once the load is in (its state change waited in the stream, and the load's answer already shows it), while what was wrong before the start stays quiet as on any start.
- *Request budget:* every by-name request of a client (re-queries, hydration, tier 3, the watchdog, `Notification` re-reads) takes a token from one bucket per environment: 5 per second, bursts of 10. A production-size tier 3 (1 473 problems: 8 requests) and a screen of rows (at most 5) fit in the burst; an outage's tier 3 of 28 000 problems (140 requests) is spread over about 26 s instead of going out back to back. The object being opened never waits. Calibrated against 2 a second, 10 a second and none (below): a request of 200 services in full costs the master about 18 ms of CPU, so the budget holds a client to about 9 % of one master core.
- *No synchronised clients* (PLAN.md §4.2; `ic-core`'s `jitter` module): after a master restart every client reloads within the same few seconds, and a timer counted from that moment would keep all fifty asking for the same 20 MB answer in the same second, interval after interval, for as long as they run. Every periodic heavy request of an engine is spread instead. The **first reconcile after a load that wasn't one** (the first load, a reload after a restart or a reconnect, `Refresh`) falls at a **random phase**: anywhere from half an interval to one and a half after the load, a whole interval wide (the average cadence stays the interval), so clients that loaded together are spread over the whole interval at once; after a failed load the phase is one to two intervals (a struggling master gets at least a whole interval's rest). **Every later interval is ±20 %** (it was ±10 %), so clients that did line up keep drifting apart rather than back together. Planned again (a reconnect after a short gap, whose session end forgot the plan, a change to quiet mode or of the interval), a reconcile keeps the point of its window it was drawn at, applied to the interval that holds now (`sync::Draw`), so a phase drawn after a master's restart isn't pulled back into ±20 % of the moment the clients reconnected together (the second master's restart in the same deploy), and repeated short reconnects don't keep redrawing from one base. The jitter never takes a reconcile below its documented minimum (5 minutes, the quiet mode's 30 minutes, a fixed setting's 60 s below 5 000 objects): where a window would start below it, it is lifted above it, as wide as before, so at the 5-minute floor the first reconcile after a load falls 5 to 10 minutes after it and the next ones 5 to 7 minutes apart (on average a little less often than the interval; the clients still spread over the whole window); larger intervals keep their windows (at 32 000 objects, about 15 minutes, the first falls 7.5 to 22.5 minutes after a load). The same ±20 % applies to the quiet status poll (every 5 minutes ±1) and to the live one (30 s ±6); a session's first status poll falls at a random phase too (15 to 45 s after the connect), so reconnecting together doesn't line up the polls. What only comes with a status poll is not spread a second time: the health reads for the trouble alerts (the `ApiListener` status and the node's features, PLAN.md E2), the features while the page is open, and the cluster nodes' states are due again from 80 % of their interval on (`jitter::carried`), so the poll whose turn it is always carries them, every 5 minutes ±1 in quiet mode as the poll itself (spread twice, half the polls would come a moment too early and leave them for the next one: 4 to 12 minutes, 7.5 on average). The randomness is each engine's own (`Tuning::seed`: random in production; tests fix it, so a run repeats exactly), and the reconnect backoff, the reload jitter and a background start's delay draw from it too. Measured with the seeded generator (`ic-core`'s `engine::sync` and `jitter` unit tests): fifty clients whose loads ended in the same second have their first reconciles in every fifth of the 5-minute window (none holds half of them), each later interval within 4–6 minutes, and ten intervals on fifty clients that started lined up are spread over more than a whole interval.
- *Reconcile interval:* `min(60 min, clamp(28 ms × objects, 5 min, 60 min) × 2^streak)`, where `streak` (0–2) counts the periodic reconciles in a row that found nothing the stream missed while it was continuous (a reconnect, a reload after a gap or a restart, or a reconcile that found something resets it). 28 ms per object keeps each client's reconcile at about 2 MB a minute on the master whatever the size: 5 minutes up to about 10 700 objects, 14.9 at 32 000 (30 and 60 with the stretch); measured, a lean reconcile costs the master 75–97 ms of CPU per 1 000 objects, so about 0.35 % of one master core per client (below). Quiet mode makes it at least 30 minutes. A fixed setting replaces the adaptive part (no stretch).

## Fifty clients on one master

**The question** (PLAN.md §4.2, *Many clients on one master*): up to 50 icygui clients on one master. Does that hurt it, and how? The answer decides between *local pacing is enough*, *the coordinator idea*, *a relay* and *neither*. The plan's rule weighs two costs apart: the **spike cost** (the master's answer times to everyone else while big loads overlap) and the **constant cost** (the master's CPU per connected event stream, at rest and in a burst). Only spikes hurt: local pacing, then the coordinator if pacing isn't enough. The constant cost hurts: only a relay helps. Both fine: neither. The thresholds were set before the numbers were read: the master stays stable and responsive for everyone, others' answers under 500 ms at the 95th percentile and under 2 s at most, no queue that keeps growing, no stall; memory is not a limit but is reported.

**Measured** 2026-10-11 with commit 75a4038's engine (today's fixed pacing, with the random phase and ±20 % jitter of *No synchronised clients*; adaptive pacing isn't built), plus instrumentation only (added with this section: every load logs how long it took and how many objects it found that no event had announced; every periodic reconcile logs what it found, field by field, and when the next one is planned). Scripts, raw data and the analysis are in `contract/scale/` (`fleet.sh`, `fleet_*.py`, `fleet-data/<run>/`); `python3 contract/scale/fleet_analyse.py contract/scale/fleet-data/<run>` prints every table below from the raw data, the fits and worked-out numbers included (CPU per reconcile, the share of new TLS connections, the quiet / live split, each burst fit). **Settled** the same day after a review: the probes' stalls re-scored over every second, the constant cost measured again on a dedicated master-01 with timed bare streams (`fit-dedicated`), and the verdict restated (each change is named where it applies).

**Setup.**
- *The master:* the demo cluster (`demo/docker-compose.yml`) at the user's size, `ICYGUI_DEMO_SCALE_HOSTS=2000`: 2 278 hosts and 32 934 services (the scale workload's 2 000 × 15 in the master zone plus the demo's own estate and churn, about 110 check results a second), Icinga 2.15.6, master-01 and master-02 an HA pair (both check), three satellites. Every client talks to master-01. Never anything but this disposable cluster: the scripts and the harness refuse a URL off this machine, a node that isn't the compose project's `master-01`, and one where the fixture-only `viewer` user can't log in.
- *The machine:* 4 vCPUs (Xeon @ 2.1 GHz), 15.7 GiB, no swap, nothing else running, no build during a measurement. The cluster's six containers were pinned to cores 0–1 (`docker update --cpuset-cpus`), everything on the client side to cores 2–3 (`taskset`): the clients, the probes, the samplers, the storm generator. master-01's numbers come from its own cgroup (`cpuacct.usage`: CPU time, so 1.0 is one core busy; `memory.usage_in_bytes`), sampled every second.
- *The clients:* real `ic-core` engines, all in one process (`ic-core`'s ignored `fleet` test, a release build without LTO, `MALLOC_ARENA_MAX=2`), each with its own tiered load, event stream, timers, request budget and SQLite event log; production `Tuning` with a random seed per engine, default settings and dashboards, one URL (master-01), the API user `icygui-demo` (the user guide's permissions, no `filter-expression`). *Live* is a window on screen (every event type); *quiet* is a window hidden in the tray (`SetQuiet(true)`). Live engines open a random object about every 2 minutes (`Command::Focus`), as someone glancing at a dashboard does. Starts are the app's: `Start::User` for a window opening, `Start::Background` for a start at login (its own random wait of up to 90 s at this size). The mix at rest is about a tenth live (5 of 50), as in a team where most windows sit in the tray.
- *Everyone else:* two probes every second (closed-loop in these runs: each waited for the previous answer, re-scored over every second, see *Starts*; open-loop since the settling), each on a fresh TLS connection, at real-time priority on the client cores (so they time the master, not the client side's CPU): another client's small **by-name** query (one service, two attributes, as in the 2026-10-06 *starts* measurement) and an **Icinga Web style** request: the command Icinga Web's API transport sends for *submit passive check result*, `POST /v1/actions/process-check-result` with a filter (`host.name=="…" && service.name=="…"`), as `demo-admin`. Icinga Web reads from Icinga DB, which the demo doesn't run; through the API it only sends commands, so a command is what it would wait for. The command flips a marker service (in a downtime, so nobody is notified) between OK and CRITICAL every second; every engine records when it saw each flip, which gives the **delay from a check result to each client**.
- *Icinga's own numbers:* `/v1/status/ApiListener` of both masters (HTTP clients, JSON-RPC relay and sync queues, work queue rate) and master-01's `/v1/status/CIB` every 5 s, and master-01's log (`WorkQueue` lines, `JsonRpcConnection` semaphore waits, connection timeouts).
- *Bursts:* passive check results through master-02's API (`process-check-result` by `host.vars.rack`, 750 services a rack), flipping whole racks CRITICAL and OK every second: every result is a soft state change, so nobody is notified and nothing stays broken; master-02 relays them to master-01 as its own checks would be.
- After each restart of master-01 the demo's seed script was stopped: it re-reads the cluster with full object queries every 5 s for up to 4 minutes after a start, which no real master has.

The runs (each in `fleet-data/`): `steady` (A: 0, 1, 10, 25 and 50 clients, 30 minutes at 50, then a burst), `events` (50 clients, a 750/s burst, then all 50 live), `restart-50` and `restart-40` (B: a restart of master-01, then a configuration reload, with 50 and with 40 clients), `morning` (C: 50 window opens over 3 minutes on a freshly started master, then 50 starts at login at once), `fit`, `fit-5000` and `fit-dedicated` (D: the constant cost of 0, 10, 25 and 50 bare event streams at rest and in a burst; the last on a master-01 with two cores of its own), `reconcile` and `quiet_reconcile` (25 and 12 clients with the periodic reconcile at 5 minutes, to see what reconciles find and what they cost).

Twelve at once put others at 4–5.7 s; twenty-five at once at 5–12 s, and stalled master-01's cluster link for up to 17 s (the satellites' and master-02's JSON-RPC messages waited on its semaphore), the worst stall of all the runs. The window opens of a real morning come over minutes and stay under the thresholds at the 95th percentile, but single answers still took 2.4 s.

A soft state change is two events on a live stream (`CheckResult` and `StateChange`), so this is about 40 µs per event written, of this 2.1 GHz Xeon. A live engine costs more at rest than its bare stream (9.5 against 5.1 milli-cores) because of its polls and the objects its user opens. A quiet stream gets no `CheckResult` events, so at rest it costs a sixth of a live one; in these bursts, where every result was a state change, it still got half the events. In a real mass re-check most results don't change the state, so quiet streams would get almost nothing.

So the constant cost is small at rest: fifty clients, a tenth live, cost the master 0.08 cores more than none, and all fifty live 0.47. In a burst it is proportional to state changes × live streams: 50 live streams at 1 500 state changes a second need about 6 cores to keep up, at 2 250 about 9 (the dedicated master-01 had 2, hence its six minutes at its limit), at 5 000 about 19; a realistic team (5 live, 45 quiet) at 5 000 check results a second, mostly without a state change, about 1–2 cores. It didn't slow anyone else's answers on the dedicated master-01; it delays the streams themselves, by up to a minute after a large burst.

**At rest the delay is Icinga's own, and it depends on the stream.** A busy live stream is written in batches 5 s apart: the bare live stream's writes came 5.0 s apart (median), and live engines saw the marker every 5.04 s with its delay spread evenly over 0–5 s. A quiet stream, with only a few events a second, was written at once about a third of the time and in 5 s batches otherwise (bare quiet stream: writes 1.0 s apart at the median, 5.0 s at the 95th percentile; quiet engines saw the marker every 1.03 s, a raw delay median of 0.33 s and p95 4.1 s in `steady`). ### Periodic reconciles: overlap and what they find

**Spread.** The *No synchronised clients* fix holds after a restart, by the planned due times: each of the 40 clients planned its next reconcile once at the reconnect and again after its reload (which replaces the first plan); the 40 final plans fell due 13.8–61.7 minutes after master-01 answered again, at most 5 in any one minute (10.2–61.7 minutes and again at most 5 after the reload). Quiet clients' next reconcile came 32–62 minutes later, live clients' 10–26 minutes later. These are planned times: no periodic reconcile fired within the 10 minutes each phase lasted, so real firings after a restart weren't watched.

**Cost.** A periodic reconcile is a lean load of every object: about 4 s (median 4.1 s, at most 5.8 s) and **about 2.1 s of master-01's CPU** each (`reconcile`: 91 reconciles of 15 live and 10 quiet clients at the shortest interval the settings allow, 5 minutes, over 40 minutes; `fleet_analyse.py`'s `reconcile_cost`: master-01's CPU in the seconds a reconcile ran against the seconds none did gives 2.13 s, a fit of each second's CPU on the number of reconciles running 2.15 s; `steady`'s 16 reconciles at 50 clients 2.15 s). At 2.3 reconciles a minute others saw 54 / 82 / 166 ms (median / p95 / max) and master-01 used 0.39 cores; the 12 quiet clients of `quiet_reconcile` at 5 minutes: 56 / 68 / 91 ms (web max 924 ms once), 0.26 cores. Today's intervals at this size (live clients every 10–26 minutes, quiet ones every 30–60) mean about 1.3 reconciles a minute for fifty clients, 0.05 cores; a flat 5 minutes for everyone would be 10 a minute, about 0.35 cores on average and 0.7 reconciles running at any moment: by these numbers within the thresholds, but not measured at fifty.

Two of those classes are inferred, not proven: a state change counts as *on its way* when Icinga says it began at most 10 s before the reconcile (the 7 found began 2.6–4.1 s before); a soft → hard change in the same state is never counted as missed, and the 6 found came 62–65 s after their soft state began, with the demo's 60 s retry interval, so their hard change was 2–5 s old. The peak was 3.1–3.65 GiB in the reload wave after a restart, 2.4–2.7 GiB for a morning.

### What this machine can't show

- **The master's CPU is capped at two cores, shared with master-02 and the satellites** in every run but `fit-dedicated`. In the restart's reload wave master-01 used about 1.5 cores, in bursts master-02 took up to 1.5 cores generating the results, so the answer times under load are those of a master with less than two cores. `fit-dedicated` gave master-01 two cores of its own for the bursts (and showed that the shared cores, not the streams, made `fit-5000`'s 528 ms); the spikes (reloads, starts) ran on the shared cores only. A real master with more cores will look better in the spikes; how much better is not measured.
- **The client side is one process on two cores and 13 GiB.** 50 engines in a burst or all live saturate it: the delays in those rows are the client side's, and memory ran out twice (after the 1 500/s burst in `steady`, and 123 s into the reload wave of `restart-50`; the harness has the lowest OOM priority, so Icinga was never touched). That's why the restart and reload with fifty were measured only up to two minutes, and in full with forty.
- **No burst of 5 000 state changes a second:** the generator (master-02's API) reached 2 200–3 500 a second on the shared cores and 2 000–2 250 on a core of its own (`fit-dedicated`); 750 and 1 500 a second were measured with 50 engines, up to 2 250 with 50 bare streams.
- **One machine, no network:** loopback, no latency or bandwidth limit. Fifty laptops over a VPN read their streams more slowly, so Icinga buffers more per stream.
- **One API user for all clients**, no Icinga DB or IDO writer on the master, the demo's checks only (about 110 results a second); a production master does more besides.
- **Runs of 5 to 40 minutes**, not days: a slow leak or a daily pattern wouldn't show.
- **docker's port proxy.** The daemon runs with its userland proxy, so every request to the published ports (the clients, the probes, the storm) went through `docker-proxy` processes. They sit outside master-01's cgroup (the CPU numbers are master-01's alone), but in the runs before the settling they inherited dockerd's affinity to all four cores, so in the phases where the client side was busy (bursts, all live, the reload wave) they competed with it and could take cycles on the cluster's cores; the answer times there hold some of that. Total cluster CPU never went above about 2.0 cores, so the cpuset held. Since the settling `fleet.sh` pins the proxies to the client cores, samples their CPU (`procs.csv`) and logs every container's cpuset in `actions.csv` (before, the line was lost: `start_side` emptied the file after `pin_cluster` wrote it).
- **Not measured at all:** the reload after a reload of the master with fifty clients (only forty), and PLAN.md §4.2 (1)'s by-name batch loading against the memory peak (it belongs to step (b), where the batches are built).

### Verdict (PLAN.md §4.2 rule)

Restated after the settling of the review (2026-10-11): the thresholds are judged on every second's slot (the closed-loop probes hid stalls behind single samples), and the constant cost on a dedicated master-01 (`fit-dedicated`).

**Spike cost: hurts.** Every situation where big loads overlap breaks the thresholds agreed beforehand:
- the **reload wave after a master restart or reload**: in the 3 minutes after, others' 95th percentile was 4.3–21.6 s over every second (17.8–25.6 s in the restart with fifty's first 90 s), single answers took up to 30 s, and **master-01's cluster link stalled**: the JSON-RPC messages of the satellites and of master-02 waited 10–13 s on its semaphore, from 40-client reloads on. The restart without clients is harmless, so this cost is entirely the clients' reloads, which only the status poll's random first phase spreads (15–45 s, too narrow);
- **window opens at the same moment**: 25 at once put others at 4.8 / 8.7 s (p95 by-name / web) and stalled the cluster link for 17 s, the worst of all the runs; 12 at once 3.9 / 4.7 s; 5 opens and 45 starts at login 1.5 / 2.0 s;
- **fifty starts at login** in today's 90 s window: 661 ms at the 95th percentile (1.0 s in the worst minute) and 3.0 s at most;
- a real morning (50 window opens over 3 minutes) stays under the 95th percentile threshold (130 ms), with two single answers over 2 s (2.4 s).

**Constant cost: it doesn't hurt the master's other users at what this machine can produce; it delays the streams.** At rest it is small (1.7 milli-cores per client in the usual mix, 9.5 for a live one; 0.08 cores for fifty) and steady state with fifty clients was indistinguishable from none for everyone else (52 / 64 / 92 ms against 52 / 60 / 68 ms over 30 minutes). In bursts it is about 50–80 µs per state change and live stream (most likely about 77 µs). On a master-01 with two cores of its own, bursts at 2 000–2 250 state changes a second to 0, 10, 25 and 50 live streams left others at 95 ms or less at the 95th percentile and 378 ms at most, with no stall, even while master-01 spent six minutes at its limit writing the burst out; the 528 ms of the shared-core run came from master-02 generating the results on the same cores. What the bursts do cost is the streams' own delay: the master owed fifty live streams minutes of writing and delivered up to 57 s late (p95 38 s), quiet streams too (p95 30 s), in per-stream queues that Icinga's queue metrics don't show. That is not one of the agreed thresholds (others' answers, Icinga's queues, stalls), but it is the one cost a relay would cut and pacing can't.

**So, by the plan's rule: only spikes hurt → local pacing** (PLAN.md §4.2 1b, step (b)), then the same measurement again (step (c)); **the coordinator idea** only if step (c) still breaks the thresholds. **No relay on these numbers, conditionally:** the constant cost is settled up to about 2 250 state changes a second on a two-core master, not at the plan's 5 000 a second (about 19 cores of stream writing for fifty live streams by the fit), which this machine can't generate. The relay question reopens if step (c), or a run on a bigger box at 5 000 a second with fifty live streams on a dedicated master, puts others' answers over the thresholds; and the minute of delivery delay after a mass outage is a product question for the user (it isn't an agreed threshold), with quiet mode as today's lever (in a real mass re-check most results change no state, and quiet streams get only state changes). Step (c) repeats `fit-dedicated` and reports the master's own delivery delay next to the answer times.

What the pacing has to cover, from these runs:
1. **The reload after a restart or reload of the master** is the worst case. A restart's reload is requested with no jitter (`request_reload`, `ReloadCause::Restart`); the only spread is incidental, the random phase of the session's first status poll (15–45 s after connecting), where the restart is detected: in the data 40 reloads started over 35 s and each took a minute because they overlapped. Pacing has to replace that with the probe-first wait and batching of the start, with a spread wide enough for fifty clients.
2. **The bulk load of `Start::User`** (after the first rows the user needs; the plan already keeps the window's own first answer unpaced): twelve at once break the thresholds, twenty-five stall the cluster link.
3. **`Start::Background`**: its 90 s window breaks the 95th percentile threshold at fifty; adaptive pacing replaces a fixed window that would otherwise have to grow with the team.
4. **The periodic reconcile:** cheap (2.1 s of master CPU each) and, at today's intervals, harmless; nothing was missing from the live stream, and the quiet stream's gap is reachability-only changes.

**Side findings for the plan.**
- *Reconcile intervals* (PLAN.md 1b, *Question the long reconcile intervals*): the spread across clients didn't protect anyone measurably at today's rates (a reconcile costs the master about 2.1 s of CPU; at 2.3 a minute others' answers stayed at 82 ms p95), and shorter intervals wouldn't have caught drift in the live stream: none was found there; a periodic reconcile does correct quiet mode's missed reachability changes. A flat 5 minutes for fifty clients would cost about 0.35 cores on average, unmeasured at that rate. Evidence for neither direction beyond that; the count check and the rare safety pass stay a reasonable design, and the comparison should run on the paced engine of step (c).
- *The constant cost depends on live streams*, so quiet mode is already the lever that keeps it small: fifty windows on screen cost Icinga about twelve times what fifty quiet ones do at rest (9.5 against 0.8 milli-cores each), and more in a burst. Worth keeping in mind for the relay question if teams leave many windows on screen.
- *Not decided here, needs a bigger box:* the burst of 5 000 state changes a second, and the spikes on a master with its own cores.

## Heartbeats

**What they cost.** A heartbeat is one `dummy` check per interval on Icinga (no plugin runs) and, on a live stream, the `CheckResult` events icygui receives anyway. On a quiet stream, Icinga's stream `filter` names the heartbeats, so only their results come along (`event.type != "CheckResult" || (event.host == "…" && event.service == "…") || …`): a few hundred bytes per beat. An API user without `filter-expression` can't filter the stream; icygui then reads the beats' `last_check` with one by-name request per interval while quiet (through the request budget). Those polls are spread like every other periodic request (*No synchronised clients* above, ledger row 99): the first falls at a random phase (half an interval to one and a half after the stream changed), each next one 80–100 % of the interval after the previous (`jitter::within`), never later. Fifty clients that went quiet together drift apart, and no beat is read after its deadline (its last run + twice the interval + its allowance; the jitter only ever polls early, which costs at most a fifth more requests). A missed beat costs one more such request; a reconnect only follows when that request shows the beat ran but its result didn't arrive.

**The time budget** (`ic_core::heartbeat`, PLAN.md §4.2 B2 as written): each beat's deadline is its last arrival + its interval + an allowance. Every beat that arrives on the stream records two numbers from Icinga's own times: its scheduling latency (`execution_start − schedule_start`) and its delivery delay (arrival − `execution_end`). The delays are measured against the smallest delay of the window, so the clock offset between icygui and Icinga cancels out. The allowance is `max(5 s, 3 × p99)` of latency + delivery over the last 50 beats, capped at half the interval. A beat past its deadline is *late* (shown, never alerted by itself); the REST query goes out 10 s after the deadline, and a fresh `last_check` gets a second look 5 s later before the stream is reconnected.

Why these two numbers and not the gap between arrivals (decided in the stage 4 review, 2026-10-10): a gap-based lateness (arrival − previous arrival − interval) is poisoned by every lost or late beat. One beat that never came puts a whole interval into the 50-beat window and drives the allowance to its cap exactly when the stream is flaky; a reschedule after a reload does the same. Icinga's per-beat timestamps don't care about gaps, and Icinga keeps `next_check` on the interval, so the scheduling drift left over stays far under the 5 s floor. The *gap − interval* column below is measured data from the calibration, not the rule.

**What the numbers say.** Running a beat takes milliseconds; what varies is its delivery: results reach the stream up to 5.0 s after they ran, never later, idle or loaded, live or quiet (a busy live stream delivers later on average, 2 s, but not later at the tail). The allowance therefore never needs more than its 5 s floor for a 10 s beat, and learns 12–15 s for a 30 s beat from its occasional slow delivery. In two hours of watching, two beats were *late* for a moment (a 10 s beat whose delivery took the full 5 s; shown on the page, never alerted) and none reached the REST query, so the defaults hold: 5 s minimum allowance, query 10 s after the deadline, 5 s second look, 30 s beats recommended (10 s at the least). Raising the minimum allowance would only delay real alerts; the query, not the deadline, is what decides.
