# Requirements checklist

Every requirement has a stable ID. The final production-readiness audit checks each one against code and tests and records evidence. Requirements marked *(v1)* belong to M7 and come after rc1 (PLAN.md §4); everything else is required for rc1. Sources: PLAN.md (decisions D1–D9, sections 1–3), the design (`design/project/*.html`, `design/chats/chat1.md`), docs/architecture.md, and the user's instructions in the planning conversation.

## Connection and environments

- **ENV-01** Several environments can be configured; every one runs its own engine in the background (NOTE-08) and exactly one is active: the one the window shows. Switching happens from the footer status (environment switcher), the palette or the tray, never from the sidebar (D1, D2), and is instant: the environment's objects, connection and notifications are there already, nothing reconnects or reloads.
- **ENV-02** Add/edit/delete environment: name, URLs (https only; ENV-12), auth (basic username + password, or client certificate and key files), TLS (CA file and system roots for every URL; pinned SHA-256 and server-name override per URL), author name. Leaving the editor with changes asks first.
- **ENV-03** Passwords live in the OS keychain (macOS Keychain, Secret Service); never in config files or logs. Deleting an environment deletes its secret and its event log, also when the app quits right after.
- **ENV-04** "Test connection" shows user, version, permissions and missing permissions, and per URL the node that answers and how much of the cluster it sees (ENV-12).
- **ENV-05** On a TLS failure (unknown CA or name mismatch), the certificate's fingerprint, subject, issuer and expiry are shown, with "Trust this certificate" (sets the pin of the URL whose server presented it). A pin mismatch shows both fingerprints.
- **ENV-06** The footer's environment switcher (it looks and behaves like a button: hover and pressed states, a chevron): the environment's name, then the connected node's name and the age of the last event (`● prod master-01 2s ⌄`), the dot coloured by health (connected / stale > 30 s, except in quiet mode, where the stream may be silent for minutes (PERF-09) / reconnecting / failed); while not connected, what the connection does (`retry in 12s`). Nothing in it moves with the state: a long node name is cut short (its first DNS label is shown, up to about twelve characters; the environment's name gives way to it), never the age. The node shown is the one icygui is connected to: after a failover, the master that took over. Clicking it opens the connection details, the cluster's nodes and the switcher. *Nodes:* every master and satellite (agents left out), one per line with a dot (green while connected, the critical colour when not, grey when the node icygui talks to can't tell) and its zone dimmed; the node icygui is connected to has the selected-row background; a long list scrolls. Kept current by one small request per status poll (every 30 s; every 5 minutes for an environment off screen, quiet or not, and for the one on screen while its window is hidden in quiet mode, whose status poll runs every 5 minutes; asked again at once when it comes on screen). *Environments:* every saved environment with its health, its node and last event (`quiet` instead of the age for an environment in quiet mode, PERF-09; the environment switched to, or on screen when the window comes back, counts as live at once, so the footer shows its age, never `quiet`), the one on screen with the selected-row background (no check marks: every row lines up); no notification or object counts (that is the notification centre's job); at the right a gear (always there, dimmed, brighter on hover) opens that environment's settings without switching, and with several environments a bell on hover (a bell-off, always, while muted) mutes or unmutes it (ENV-01, NOTE-08); *add environment* at the end. The chevron turns the accent colour while another environment has unread notifications (colour only; the tooltip names them, without counts). The popover keeps its width whatever the connection says (long texts are cut short, their tooltip has them in full) and fits any window above the footer (the node and environment lists scroll; adding stays reachable).
- **ENV-07** Automatic reconnect with backoff; banner with retry countdown and "Retry now". Auth failure and TLS failure stop retrying and show actionable banners.
- **ENV-08** First run without environments shows an onboarding form.
- **ENV-10** `icygui --demo` runs the full app against a built-in, in-process mock environment (the design's prod-cluster scenario with live simulated changes, storms and notifications). No Icinga or credentials needed; clearly labelled as demo in the UI (a *demo* chip in every dashboard's header of its own environments, the window title, the connection details, the tray).
- **ENV-11** README screenshots are generated from demo mode (`cargo xtask screenshots` under Xvfb), so they stay current.
- **ENV-12** An environment is one Icinga cluster with one or more API URLs in order of preference, for any topology: a single master (one URL, as before), an HA pair in one zone, a master with satellites in child zones, a load balancer or round-robin DNS in front. On every connect the client finds the node behind the URL (`node_name` from the status → its endpoint → the zone listing it): a node in the top-level zone (no parent, not global) gives the **full** view; a node in a child zone a **partial** view, allowed but always labelled (`partial view: zone ams`; never looking complete); the URL choice prefers full-view nodes and takes a partial-view node only while none of those answers, and keeps trying the preferred ones gently (growing waits with jitter) to switch back. When the API user can't read the status or the zones, the view is "not verified" instead of guessed. The cluster's CA covers every node (recommended); pins and server names are per URL. Settings with a single `url` migrate to `urls`. The environment editor adds, reorders, removes and tests URLs; the footer shows the connected node. Falling back to a partial view never loses a notification: what changed outside the zone meanwhile (a new problem, a recovery) notifies once a full-view node is back, and nothing the cluster had all along notifies again. A preferred node that accepts connections but doesn't answer is passed over within seconds and not waited for on every reconnect. With pinned certificates, a URL whose certificate isn't trusted is offered for trust while the engine keeps retrying the others.
- **ENV-09** Works with a least-privilege API user without `filter-expression` (Icinga 2.17 default). Buttons for actions the user may not run are disabled with an explanation.

## Live data

- **LIVE-01** Initial load, then the event stream; changes appear within about a second without polling.
- **LIVE-02** Periodic reconcile (configurable interval) and reconcile after reconnect; missed changes are detected.
- **LIVE-03** Objects created or deleted in Icinga appear or disappear.
- **LIVE-04** 20 000 services stay smooth: virtualised lists, nothing per frame proportional to the object count.

## Scale (docs/performance.md)

Production scale is 2 000 hosts / 30 000 services; the numbers were measured against a real Icinga 2.15.

- **PERF-01** Tiered loading: hosts full, services lean, problem details by name. Problem lists are complete within 5 s on a LAN, and the UI fills in progressively with visible load progress.
- **PERF-02** Live changes appear in the UI within 1 s of Icinga emitting the event; no polling for state.
- **PERF-03** The event pipeline never stalls Icinga's stream. It absorbs a 50 000-event burst in under 3 s and costs under 5 % of one core in steady state (~110 events/s).
- **PERF-04** No per-event re-queries (`vars_after` is used). Re-queries happen by name only for config changes, unknown objects and on-demand hydration of visible rows and opened panes. Two exceptions: a `Notification` event re-reads that object's `Notification` objects by name (four small attributes; deduplicated, at most one round in flight, 200 names per request), because the event doesn't name the `Notification` object it came from (only its command) and can't be applied exactly (PANE-06; docs/architecture.md, sync engine step 7); and a notification icygui shows fetches its object in full once (PERF-09's prefetch: one small request, at most 10 a minute, none for silent ones). Unknown objects are looked up in whole batches, so objects hidden from a filtered API user cost a request per 200 names, less and less often. Every by-name request takes a token from the client's request budget (PERF-09).
- **PERF-05** Master-friendly: one event stream per client; lean reconcile at an interval that follows the installation's size (28 ms per host and service, 5 to 60 minutes: 5 minutes for small installations, about 15 at 32 000 objects), doubled up to twice while the event stream stays continuous and the reconciles find nothing it missed (at most 60 minutes), at least 30 minutes in quiet mode (PERF-09); on reconnect after a long gap with jitter, and on Icinga restart; never periodic full-attribute reloads. Load pacing scales with the installation, never by fixed times: background starts wait a random size-proportional delay and every by-name request shares a request budget (PERF-09).
- **PERF-06** Client memory under 400 MB at production scale; 30 000-row dashboards scroll smoothly; dashboards are evaluated incrementally.
- **PERF-08** Freshness watchdog: every object's deadline is Icinga's `next_update`, reset by every check result (manual or scheduled, by anyone). Overdue objects are re-queried individually by name, and objects that are still overdue are shown as "late" in rows and panes. Not in quiet mode (PERF-09: no check results move the deadlines; late markers may be stale there); after it, every object gets one interval before it is looked at again, so waking up costs no re-query storm.
- **PERF-09** Quiet mode (on by default; the general setting *Quiet mode when hidden*): every environment that isn't on screen, and the one on screen while the window is hidden (closed to the tray, or not shown at all as the system reports it: minimised, on another virtual desktop or Space, a sleeping display, on macOS and on X11 without a compositor also completely covered; after 30 s out of sight, so a quick look elsewhere doesn't switch the stream; not when the window is merely unfocused or partly covered), follows Icinga with an event stream without check results: state changes, acknowledgements, comments, downtimes, flapping, Icinga's notifications and configuration changes still arrive at once, so notifications are never delayed (about 99 % less stream traffic per client). Quiet mode polls the status every 5 minutes, reconciles at least every 30, runs no freshness watchdog and no hydration, publishes snapshots every 2 s and keeps only the dashboard memberships notifications depend on. Stale while quiet: check outputs, last-check times, late markers. No per-environment or per-dashboard exception. Switching between quiet and live (hiding or showing the window, switching environments) never loses or repeats an event: a switch without proof that the old stream delivered everything (no event came on both streams within 2 s) is checked against Icinga's state counts, and a mismatch reloads, so a stream that stalled or lagged before the switch loses nothing either. *Instant wake-up:* an object that changed state is fresh already (its state change carried its check result); a notification shown prefetches its object's full details (one small request, none beyond the storm threshold); the object being opened (a notification clicked, the palette, the selection) gets one by-name request ahead of everything else, then the rows on screen whose output may have changed (however many problems there are), then the remaining problems whose output may have changed (at most 1 000), while the full stream reopens; the pane never blocks and shows an "updating" hint only after about 300 ms, in a fixed slot of its header; moving the list's cursor with the keys asks only for the row it rests on. Showing the window counts at once, before anything opens in it. *Load pacing that scales with the installation:* a background start (launch at login) waits a random delay of up to 3 s per 1 000 services (at most 90 s; under a second for small installations; without `status/query` the count is estimated from the hosts) before its first load, and a start the user opens never waits; a problem that begins while it waits notifies once the load is in; every by-name request of a client shares a request budget (5 per second, bursts of 10) that small installations never reach, the object being opened always first. Measured against `ic-mock`'s `large` scenario, and against the local Docker Icinga: 20 simultaneous starts, 20 clients fetching an outage's problem details at several budgets, the master's cost of a lean reconcile (docs/performance.md).
- **PERF-07** Reproducible benchmarks: `contract/scale/benchmark.sh` (real Icinga) and `ic-mock`'s `large` scenario with burst mode. Release-mode performance tests run in nightly CI.

## Sidebar and dashboards

- **DASH-01** The sidebar matches the design: search, groups (folders) with active highlight, chevron, + and ···, dashboard rows with state dot (worst unhandled), label and unhandled count, footer icons (sidebar toggle, notification centre, environment status, +).
- **DASH-02** Groups: create, rename, collapse, reorder, delete (with confirmation), per-group notification setting.
- **DASH-03** Dashboards: create (+ on a group), edit, rename, duplicate, move to another group, reorder, delete, per-dashboard notification setting.
- **DASH-04** The dashboard editor has name, hosts/services, filter in Icinga's language with live validation (error position) and live match count, problems only, hide handled, sort, group by. Its changes are never dropped without asking: showing something else or switching environments keeps them for the next edit (in their environment).
- **DASH-05** Default dashboards for a new environment ("overview": problems, host problems, all services).
- **DASH-06** Export and import dashboard groups (files), with fresh ids on import.
- **DASH-07** Sort menu (severity, last state change, host, service; direction) and the "handled hidden" toggle are persisted per dashboard.
- **DASH-08** Group-by (host, host group, service group) with headers.

## Lists and panes

- **LIST-01** Rows as in the design (2a): 22 px state circle (filled = unhandled, hollow = handled), time in state, `service on host`, output (ellipsis), right tag (ack author, downtime, flapping).
- **LIST-02** The summary bar shows counts per state with dots, and the handled toggle.
- **LIST-03** Keyboard: j/k and arrows move, Enter opens, Esc closes, x multi-select, shift-click range; selection survives updates.
- **PANE-01** Service pane as in 2b: state, name, host link, duration, hard/soft attempt; action buttons with key hints (a, d, r, c) that keep their places whatever the state (the first slot holds *acknowledge*, *remove ack* or a disabled *acknowledge* at one width; an action on its way shows `…` in its key's place; while rows are marked the hints stay empty, the keys acting on the marks); plugin output and long output; perfdata table with threshold colouring; check details; comments; downtimes; vars; groups; notes and links.
- **PANE-02** Host pane as in 2c: state, address, uptime/output; actions; tabs: services (OK collapsed into "+ N more ok"), history, vars, config (read-only check config and feature flags); parents and children from dependencies.
- **PANE-03** "↗ open as tab" pins an object in the sidebar's "open" section; pinned tabs persist.
- **PANE-04** History tab from the local event log ("recorded locally since …").
- **PANE-05** Copy name, output and filter expression; open notes/action URLs in the browser.
- **PANE-06** Service and host panes show who was notified and when (design 2b "notified" row): the last notification time and its recipients from Icinga's `Notification` objects (`last_notification`, `notified_problem_users`), or "not notified".

## Actions (runtime operations only; D6)

- **ACT-01** Check now (force), on one object or a selection.
- **ACT-02** Acknowledge (comment, sticky, persistent, expiry; never asks Icinga to notify) and remove acknowledgement.
- **ACT-03** Schedule downtime (start/end with presets, fixed/flexible + duration, all services, child options, trigger) and remove downtimes (single, or all for the selection).
- **ACT-04** Add comment and remove comment.
- **ACT-05** Submit a passive check result (state, output, perfdata).
- **ACT-06** Run command (check/event command, endpoint defaulting sensibly, macros, TTL) behind a confirmation.
- **ACT-07** Bulk actions on multi-selection. Results show as toasts with per-object failures; changed objects refresh within about a second.
- **ACT-08** The client never calls `objects/modify`, config packages, object creation or deletion, the console or process restart. Icinga's feature flags are shown read-only.

## Notifications (D4, D5)

- **NOTE-01** Native OS notifications (macOS UNUserNotificationCenter from the app bundle; Linux XDG via D-Bus) with Acknowledge and Open buttons, from every environment (NOTE-08), never delayed by quiet mode (PERF-09); what is already wrong when an environment's engine starts doesn't notify, but a problem that begins after its event stream opened does, also during its first load or a background start's wait (it notifies once the load is in); clicking switches to the notification's environment and opens the object's pane (window recreated if closed), complete at once (the notification prefetched it; PERF-09); *Acknowledge* opens the acknowledge dialog for the object in its own environment, without switching, and the acknowledgement goes to that environment's Icinga.
- **NOTE-02** Rules per environment (default), group, dashboard ("thread") and object (watch / mute with expiry), with inheritance as specified in docs/architecture.md (ic-rules).
- **NOTE-03** Conditions: states, hard only, skip handled, acknowledgement/downtime/flapping events, minimum duration, sound.
- **NOTE-04** Recoveries only for notified problems; dedupe across dashboards; storm control with summary; quiet hours (midnight-crossing, days, allow critical); pause (30 m, 1 h, until tomorrow, resume).
- **NOTE-05** Notification centre (footer clock icon): recent notifications including silent ones, newest first under time sections (now, last hour, earlier today, yesterday, older); open the object (switching to its environment). Each environment keeps its own list; the clock's badge counts the unread notifications of the environment on screen. With several environments, chips in a bar at the bottom of the card pick the scope (`all`, then every environment; the pause chips' style, the one picked filled with the selected-row background): one environment (the one on screen when the centre opens) or *all*; a scope with unread notifications shows in the accent colour (colour only: no dot, no count, nothing moves); chips that don't fit go behind `···` (the bar never wraps); the heading counts the scope's unread notifications. A gear at the right of that bar opens the notification settings; the heading, the pause row, the list and the bar line up on one grid. Entries: a bright title while unread; where they matched without repetition (`overview`), with the environment in front only in *all*; a click on that label shows only that place's notifications, again all; silent ones dimmed (a hollow dot) with their reason (`silent · storm`, `quiet hours`, `paused`); a storm's notifications collapsed into its summary, which expands. *Mark all read* marks what the list shows; opening an object anywhere marks its notifications read. The pause row pauses every environment, or shows that the scope's environment is muted on its own (with *unmute*). The centre keeps its size and place while it is open, whatever it shows or receives, and fits above the footer in any window; while the pointer is over the list, arrivals wait until it leaves (the heading counts them), so no entry moves under it.
- **NOTE-06** Notification settings UI for every rule field, quiet hours, storm control, and the watched/muted list (v1: the settings panel's notifications page, for any environment, picked in its *environment* dropdown; changes apply at once).
- **NOTE-09** *(v1)* Desktop notifications can leave out the plugin output (Settings → notifications → *show plugin output*, on by default; off for shared screens and the lock screen): a state change then says only where it matched, its title still names the object and its state; comments of acknowledgements and downtimes and storm summaries stay.
- **NOTE-07** No notifications for the initial load; missed changes found by reconcile do notify.
- **NOTE-08** Every saved environment runs its own engine (event stream, rules, event log, notifications) from the app's start, also with `--background`, until it is deleted (its engine stops, then its event log goes); a change of its URLs, login or TLS restarts it. The active one drives the window; the others publish their snapshots less often (nobody looks at them) but notify as promptly, and cost Icinga less than the active one: one event stream in quiet mode (PERF-09: no check results) and one lean load per environment. Native notifications come from every environment for every enabled rule; with more than one environment the title starts with the environment's name (`staging · CRITICAL · disk on stg-db-01`). Pausing holds for every environment (the default); one environment can be muted on its own from the switcher or the palette, and the switcher shows it as muted (a bell-off, like a muted dashboard).

## Background and platform

- **BG-01** Closing the window keeps the app running in the tray / menu bar (configurable). Quit from the tray or the menu quits.
- **BG-02** The tray icon shows the worst unhandled state across all environments (NOTE-08); the tooltip has a line per environment (its connection, its view when short of the whole cluster: `partial view: zone ams`, *muted* when muted on its own) with its counts; the menu has Open, Pause notifications (every environment), Environments, Quit.
- **BG-03** Optional launch at login (LaunchAgent / XDG autostart) starts in background mode (`--background`): every environment quiet, each first load after a random wait proportional to the installation's size (PERF-09) until the window shows; problems that begin during the wait notify once the load is in (NOTE-01).
- **BG-04** Single instance: a second launch brings the running instance's window forward.
- **BG-05** macOS app menu (About, Settings ⌘,, Quit), Edit menu for text inputs, keyboard shortcuts with cmd on macOS and ctrl on Linux.
- **BG-06** Linux client-side window decorations matching the design; window icon; window size and position remembered.

## Look and feel

- **UI-01** Dark theme exactly per the design tokens (PLAN.md §1); IBM Plex Mono bundled.
- **UI-02** *(v1)* ✅ Light theme (PLAN.md §4.2, mock-up 03) and the theme setting: *follow system* (the default: the desktop's light or dark mode as the window reports it, switching the moment the desktop switches), *dark* or *light*, applied at once. The light theme has every token the dark one has, with the same structure (a white window, the pane and code blocks a band off it, a slightly grey sidebar, text at the dark theme's contrast steps, selection tinted towards the accent, softer shadows and backdrop). Every state colour has two shades: a fill for circles, dots, bars and squares, and a text shade for words and numbers in a state colour (`CRIT`, `late 3m`, perfdata values over a threshold, the kinds in the history), 5:1 or more on white and 4.5:1 on every light surface but the tinted selected and marked rows (4:1 there); the dark theme uses one value for both and looks as rc1 did. Every component and view takes its colours from the theme (no colour written in a view); gpui-component's controls and its Linux window frame follow the theme too. The tray icon follows the desktop, not this setting.
- **UI-03** ⌘K / ctrl-K command palette: dashboards, hosts, services, actions, environment switch, settings, pause. Every row has a mark in the dots' place: an action on an object its state dot, an action on several objects (a verb's *all N matches*, the marked rows) a several-objects mark tinted with the worst state, a dashboard its summary dot, any other command a small muted icon. Objects read as their rows do (`Acknowledge · postgres-replication`, `on db-prod-03 · critical`), never `host!service`. The open or selected object's actions are ordinary rows of that kind: they come first, also with an empty query, and show their keys (a, d, r, c); a query naming that object lists it once. A verb's *all N matches* (⌘↵ / ctrl-↵) never acts directly: it opens the action's dialog listing every object (a check too, in a dialog of its own).
- **UI-04** Relative times refresh (footer every second, rows periodically).
- **UI-05** Empty, loading and error states for every view (no environment, connecting, no permission, filter error, empty dashboard).
- **UI-06** *(v1)* A settings panel in the style of Zed's (PLAN.md §4.2, mock-up 02), replacing the two-tab dialog: it opens over the main window as a large panel (about 1080 × 760, fitted to smaller windows; ⌘, / ctrl-,, the app menu, the palette) and closes with Esc, its × or a press outside. Left: a search field, the categories general, appearance, notifications, icinga, keymap and advanced with icons, the open category's sections on a guide line (the one in view marked), *focus navbar* (⌘⇧E / ctrl-shift-e). Right: a header (the category, whom it applies to, *✓ saved* or why not, *edit in settings file*, which opens the settings file in the default editor) and one row per setting: a name, one line of description and the control at the right. Every change applies at once (no save or cancel); text fields on Enter, Tab, leaving the field or closing the panel; a value that doesn't parse shows its problem under its row and isn't applied. The search covers every category: categories without a match dim, the others count their matches, the matches are listed by `category · section` with the match marked, and they work in place. Contents: general (tray, start at login, quiet mode when hidden), appearance (UI-07), notifications (NOTE-06, NOTE-09), icinga (reconcile, event log retention, every environment with its health dot, a one-line summary and a gear opening its editor, *add environment*), keymap (UI-08), advanced (OPS-08, the version and *about*). A settings file edited by hand is taken over when the window comes back to the front (environments reconnect only when their connection changed); an unreadable edit is reported and changes nothing.
- **UI-07** *(v1)* ✅ Appearance settings, stored in the settings file (`[appearance]`, format version 3 migrating `general.theme`), each applied at once to the whole window (from the panel or an edited settings file), with a preview of the selected dashboard's rows as they look: theme (follow system, dark, light; UI-02); interface size (small, default, large: 90, 100, 115 % of the design's text and spacing everywhere: the type scale, the layout metrics and every length a view draws; hairline rules stay one pixel, window geometry is untouched); row density (comfortable: two lines with the time under a 22 px circle; compact: 32 px rows plus the rule, a 14 px circle, `service on host`, the tag, and the time in a fixed slot at the right, no output line, about twice the rows on screen; in the dashboard list, the dashboard editor's preview and the settings' preview, with the second line dropped in the host pane's services, the history and the notification centre too; the lists stay virtualised); and times in lists (relative, `14m`, or clock: since when, `13:58` today, `Oct 3` on an earlier day, the year before this one; in the dashboard lists, the previews and the host pane's services).
- **UI-08** *(v1)* A keymap file (`keymap.toml` next to the settings file) adds the user's own bindings on top of the defaults (per key context, `"none"` unbinds, actions with an argument), read at start and again when the window comes back after it changed; bindings that can't be used are skipped, counted on the keymap page and logged. The settings' keymap page lists every shortcut in effect (what it does, its keys, where), filterable by name or key, and *edit keymap file* opens it (created with commented examples).

## Brand and distribution

- **REL-01** Logo: inspired by Zed and Delta, built on Icinga's orange warning circle with the design's blue accent; a single SVG source renders the app icon (all sizes, `.icns`), the mark and the README banner.
- **REL-02** macOS releases are universal binaries with the hardened runtime. Without a Developer ID (current state) they're ad-hoc signed; with the Developer ID secrets set, they're signed, notarized and stapled (app and `.dmg`) with no code changes.
- **REL-03** Optional Homebrew tap: when a tap token is configured, the release workflow updates `Casks/icygui.rb` (macOS; clears quarantine while builds aren't notarized) and `Formula/icygui.rb` (Linux); `uninstall quit` and `zap` are correct.
- **REL-08** `install.sh` (`curl … | bash`):
  - macOS and Linux, x86_64 and arm64; latest or pinned version;
  - SHA-256 verification against `SHA256SUMS`;
  - macOS: install into `/Applications` (or `~/Applications`), quit a running instance first, re-sign with a per-machine self-signed identity (falling back to ad-hoc), needs no Xcode or Command Line Tools;
  - Linux: user-local install with desktop entry and icons, plus hints for missing libraries;
  - `--uninstall` and `--purge`;
  - never runs a partially downloaded script.
- **REL-04** Linux releases: `.deb` and `.tar.gz` for x86_64 and aarch64 with desktop entry and icons; `SHA256SUMS` (optionally GPG-signed) and build-provenance attestations for every artifact.
- **REL-05** One-tag releases: the tag must match the workspace version; the release can be rebuilt by hand for an existing tag.
- **REL-06** `icygui --version` and `--help` work without opening a window (the Homebrew formula test relies on it).
- **REL-07** The tray icon uses the logo's mark, tinted with the worst unhandled state.
